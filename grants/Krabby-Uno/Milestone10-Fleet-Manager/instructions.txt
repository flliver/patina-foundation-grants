The overall goal of this milestone is to build a fleet manager for Krab robots so we can operate and maintain multiple Seeed Robotics J4012 Orin Jetsons (and scale to many more) from a single web portal. The fleet manager must support deploying and updating the Krabby application via AWS IoT Greengrass, viewing telemetry from each device, and opening a WebRTC teleoperation session to any robot from the same portal. This extends the M7 vision/teleop work by moving the teleop UI into the fleet manager and adding device management, OTA updates, and centralized telemetry.

Target devices: Seeed Robotics J4012 Orin Jetsons (Jetpack 6 and 7 supported) (and, in principle, any device capable of running Greengrass and Docker on an NVIDIA platform). Scale: 2–10 robots for initial validation, with architecture that supports scaling to hundreds or thousands of devices.

The project should deliver:

1) A working Greengrass-based deployment path so we can pull existing Krabby Docker images from ECR and deploy them to registered devices, with support for custom image tags (e.g. image-<myhandle>-<date>) so we can push and roll out our own builds.
2) A front-end web portal (Next.js) for fleet management: list devices, view status, and drill into a device to see its telemetry and open a teleop session. The portal is backed by a small wrapper/fleet service hosted on Fargate (Docker), with ECR and a githook on push for deployment. The fleet service integrates with Greengrass (and optionally AWS IoT) to list devices and fetch telemetry; IoT is used for basic portal telemetry once per minute (krab health, IMU/pose, power, major red flags). HAL client uploads historical telemetry and camera streams to S3 (replay/training); teleop streams live video and pose only over WebRTC while a session is attached.
3) Teleop integrated into the portal: from the fleet page, open a WebRTC teleop session to a selected robot. Demonstrate with 2 robots that you can control and manipulate both from the fleet management page. The teleop view should show robot pose in addition to camera streams, and support both Bluetooth gamepad and in-browser (virtual joystick or keyboard) control.
4) End-to-end hardware-in-the-loop deployment: a githook (or CI step) that, when a new image is built and pushed, triggers a Greengrass deployment to a specific “test harness” Orin (e.g. one on my desk at home) in front of a calibration screen. The deployment runs the new image, sends a few commands to move joints, and validates that the calibration screen position moves by a small amount (e.g. 1–2"). This proves the fleet manager can actually deploy images to the fleet and provides a regression test: if something breaks the mainline Krabby image on the test harness, we can point AIs at the failure to fix the bug.
