This one is heavily based on M21. It's two major parts:

#1, replacing the serial interface inside firmware/cli.py and firmware/krabby_mcu.py with a CAN bus implementation of both, utilizing cloned/updated/cleaned up arduino.ino (now called command_handler.c and copied to the firmware/stm dir), that reads the commands over CAN, and calls the appropriate functions to handle them. This utilizes the virtual krab backend, and is completed when the new stub command_handler can be called by the new/updated cli.py and krabby_mcu.py and control the robot. 

#2 Make STM implementations of all the firmware functions handled by the virtualized backend, cleaning up and removing useless/unused code as we go (i.e. calibrate no longer is required, hold is no longer required, absolute joint position is no longer required, version is no longer required, etc.) Only send_pwm(bool direction, int power) is now required, and receiving telemetry back. SUPER SIMPLE.

Task #1

Overall, this is kind of a clean sweep, of the cli, all the way down through the firmware, in a way that does not disrupt current main.

Here's the rework from the top of the stack to the bottom. Work should be completed from bottom of the stack to the top, but work is specified in this order so you can easily understand what each system is called by.

1) Create a new firmware/stm/cli dir, move cli.py into it, and update cli.py to flash over the STM32_Programmer_CLI interface. This will require updating the update function to pull STM .elf files instead of arduino hex files off the base repo, and ensuring that we publish the elf files to that repo.
** Now you can flash the board w/ some test.elf file and see a light blink, motor oscillate, etc. 
2) Add a DBC file w/ structure set_duty(int leg, float yaw, float hip, float knee) where leg is the busID for the leg., and each float is -1.0 to 1.0, indicating direction and power. Then wire up the a new function in the new cli.py that constructs the appropriate CAN message using the generated C code from the DBC file (generated by cantools). Add 'connect()' function as well so you connect to CAN bus.
** Now you can send a duty message using CLI, and see it pop up on CAN bus (not yet received by the board)
3) add a can_handler.c to stm/core/ (new dir) and have it receive the set_duty() command. Copy over all appropriate *jog* code over from arduino.ino (now renamed to set_duty()), and have it set appropriate pins to trigger the correct TI bridge to the correct duty cycle.
** Now you can control the board via cli w/ the set_duty() function, and see the motor move.
4) Create a new telemetry_handler.c inside stm/core, copy over any useful lower level telemetry information it reads off the POT/HALL pins for each motor, assemble into a telemetry message on the DBC, include firmware version string/ID, and trigger to emit on the bus for that joint.
** Now that leg emits all joint telemetry + board version info to the CAN bus
5) Wire the appropriate pins to the simulation from M21, and show that this new interface can control the simulated robot over virtual CAN. This will probably require refactoring of the way the SIM code is called, since you no longer need to adhere to the arduino interfaces. It will also require setting up a virtual CAN bus for can_handler, telemetry_handler, and cli to all talk over. (similar to M21's serial, but using linux's standard virtual CAN bus) 
** Now you can give a joint command in via krabby cli, see it go over can bus, get picked up by can_handler, have can_handler call to SIM to move the joint, joint moves, changing telemetry, telemetry is picked up by telemetry_handler, which spits back out to CAN and back via CLI.

At this point task 1 is complete, and you have a fully functional board that via krabby-firmware cli can send duty cycles and receive telemetry to the simulated board.

Task #4

Replace the old STM flash mechanism with a new flash over CAN approach, using openBLT or similar. The idea being when the device is up on CAN, it receives the some kind of XCP connect frame, which gets picked up by can_handler.c, which resets the board into the OpenBLT bootloader, which then automatically handles reflashing and reboots.

Qwiic OLED and battery stuff is out of scope for this.
calibration is out of scope and removed from the new firmware entirely (it would be handled by the Orin now or via some kind of relay from one board)
target position is out of scope (comes after calibration)

Overall things should get much, much simpler and more direct.

Tenets
* Don't copy over code you don't need anymore, just write clean, from scratch code that does the minimal necessary to control the motors and get telemetry
* Completely abandon leg enums use CAN ID now for leg: 1 = FL, 2 = FR, 3 = ML, 4 = MR, 5 = RL, 6 = RR. i.e. krabby CLI when sending duty, is sending to an int ID. This keeps the CAN bus layer extremely simple/direct w/ no struct translations.
* Completely abandon joint enums, use motor ID for joint: 0 = yaw, 1 = hip, 2 = knee. This is nested under each controller on the can bus, and sending no command to a joint means hold that joint. i.e. you can 'set_dut(1, 1.0, 0, 0)' and it would send full power to FL yaw, hold to FL hip and knee.
* Completely abandon the concept of 'hold', hold is now just set_duty (#, 0, 0, 0)
* Completely abandon calibration, that's going to be handled by Orin
* Completely abandon role selection and telemetry relay from primary to secondary devices, every device (leg) sends its own telemetry on the bus now
* Use DBC for all CAN bus structs and auto-generate C/python code for them
* KEEP IT SIMPLE!!! Don't carry forward unnecessary abstractions from the old arduino code, just iminimal structs/abstractoins/etc to get it working cleanly and simply.
