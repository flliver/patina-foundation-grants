# Patina Foundation Grant — Krabby-Uno Milestone 17: Krab End-to-End Sensor Validation

> **Prerequisite for Milestone 15 (Sim2Real-Krab).** M17 was scoped after M15, but it must complete first: M15 assumes a calibrated robot with trustworthy joint position, current-sense, and IMU values flowing through HAL into the model. M17 builds exactly that trust on the new V0.3 MCU boards before any sim-to-real work begins.

## Grant Overview
Take the new V0.3 Krabby-Uno MCU boards (M8 PCB revision) and the three Arduino Mega + shield stacks they sit on, plug in the 18 motors received via M12 (12 linear actuators + 6 hip-yaw), and validate end-to-end that every sensor signal the locomotion model relies on is accurate, calibrated, and arriving where it needs to. The work runs as **Task 0 (octopus wiring + bench layout)** plus six substantive tasks. Task 1 brings up the three V0.3 boards with all 18 motors and fixes a known bug where the primary (USB-connected) shield is not reliably driving the LEFT/RIGHT follower shields — root-cause whether the failure is in role sync, leader→follower forwarding, or follower receive — and replaces the SYNC-based role election with **a simple EEPROM load on boot plus generic `SET` / `GET` config commands** (key-value lists in the same style as the existing `T` joints command). The operator sets each board's role with `SET role <PRIMARY|LEFT|RIGHT>`, set serials with `SET serial …` whenever they want, and Task 1 also defines a third wire surface — the asynchronous `ERR <token> <errorcode>` telemetry channel — that every subsequent task uses for fault reporting. Task 2 builds the per-joint calibration function that auto-detects whether each motor's wired sensor is a potentiometer **or** a Hall encoder (never both), records min/max stops, detects direction-flip, and returns position as a **normalized float in [0.0, 1.0]** matching what the model consumes. Task 3 drives Task 2's per-joint function through a safe sequence on all 18 joints starting from an **auto-driven "squat" pose** that splays the front legs forward, rear legs aft, and middles centered; the middles calibrate first, then front/rear after un-splaying. Task 4 runs as the **final phase of `calibrate-all`** — after Task 3's per-joint cal completes, the firmware issues a neutral-pose command (every joint → 0.5) and then lifts the body half on each leg in turn to validate current sense; failures emit `ERR <joint> <code>` via Task 1's channel; the operator inspects EEPROM cal state after the fact via `GET calibration`. Task 5 plumbs the ZED 2i's onboard IMU through HAL into `HardwareObservations.base_ang_vel_b` and `base_quat_w` — the existing `ZedCamera` only exposes RGB + depth, so this is real new work. Task 6 deploys the default locomotion image on the Orin, audits the HAL → model mapper against the now-calibrated robot, maps current-sense into the model's `contact_forces`, and captures the flail-test that M15 Task 1 picks up from.

## Why is this Important?
- **The model can only be sim-to-real'd against a robot whose values mean what the model thinks they mean.** Min/max stops, direction conventions, current-sense ranges, IMU orientation — if any of those are wrong, M15's randomization and tuning will be chasing the wrong distribution. This milestone is the calibration and trust pass that M15 implicitly assumed.
- Surfaces and fixes the V0.3 primary↔follower communication bug now, before it silently corrupts joint commands during a model run.
- Replaces the brittle SYNC-based role election with an explicit `SET role` command + EEPROM persistence; per-board serial numbers are set via the same `SET` mechanism. The foundation for any fleet fabrication where individual boards need per-board identity + calibration recall.
- Establishes a single per-joint calibration function reused by the whole-robot sequence, with a deterministic auto-squat starting pose so calibration runs cleanly from any prior state.
- Defines a single asynchronous `ERR <token> <errorcode>` telemetry channel (Task 1 §5) that any command can emit faults on, with a canonical error-code vocabulary shared across all of Tasks 2/3/4. The firmware contract stays minimal: commands in; joint telemetry, `ERR` lines, and `GET` replies out. `GET calibration` is the only path to inspect EEPROM state after a run.
- First time the parkour model drives the **real Krabby-Uno** hex through HAL with all real sensors connected — the lap before M15 starts tuning.

## Tasks
Total: **~17 dev days assigned** out of ~20 part-time working days in a month (4 weeks × 5 days). The remaining ~3 days are unassigned cleanup / integration / slop — Task 1's primary↔follower debug is the most likely place to absorb them, with Task 4's chassis-dependent step a secondary risk. Full implementation detail, exact code locations, and acceptance criteria live in the task files.

### Task 0 — Octopus wiring, layout, and physical pre-flight → [TASK-0-OCTOPUS-WIRING-AND-LAYOUT.md](TASK-0-OCTOPUS-WIRING-AND-LAYOUT.md)
**~0.5 day (range 0.5–1).** Lay out all 18 motors + 3 Megas/shields + 6 H-bridges on a single base board; wire to the new octopus 24 V bus; label every motor with its joint name; re-crimp anything that doesn't pass a connector inspection; manually jog each motor to confirm the physical path works before any firmware/SDK work. Surfaces hardware issues now, not later.

### Task 1 — V0.3 MCU bring-up, primary↔follower comms fix, board config → [TASK-1-V03-BRINGUP-AND-COMMS.md](TASK-1-V03-BRINGUP-AND-COMMS.md)
**~4 days (range 3–6).** All 18 motors driveable through `KrabbyMCUSDK` end-to-end. Root-cause and fix the known primary↔follower comms failure (prime suspect: locally-built firmware uses the 64-byte default serial RX buffer instead of 256 because `firmware/Makefile` doesn't pass `-DSERIAL_RX_BUFFER_SIZE=256` the way CI does — fix the Makefile so all build paths produce identical binaries). Replace SYNC election with USB-as-primary; add generic `SET` / `GET` commands plus side-suffixed variants `SET_LEFT` / `SET_RIGHT` / `GET_LEFT` / `GET_RIGHT` that route directly to the corresponding follower over Serial1/Serial2 — no nested commands. JOINTS-style key-value lists (`SET role LEFT`, `GET role serial version`, `SET_LEFT role LEFT`). `SET serial` is rejected — Task 3 owns serial-write as part of calibrate-all. Comms debug is the main schedule risk.

### Task 2 — Per-joint calibration (one sensor per motor, direction flip, EEPROM, normalized [0.0, 1.0]) → [TASK-2-PER-JOINT-CALIBRATION.md](TASK-2-PER-JOINT-CALIBRATION.md)
**~3 days (range 2.5–4).** Single-joint calibration the whole-robot sequence will call repeatedly. Sweeps to both end stops; for pots, detects reversed wiring and stores a flip flag in EEPROM (applied at `getRawPos()` read); for Hall, decodes A/B quadrature into a signed count (replacing today's edge-only count in `hall_hw.cpp`) and verifies repeatability across two sweeps. Cal data persists per-joint in a new `JointCalBlock` with magic + schema version + CRC. Normalized `[0.0, 1.0]` float is confirmed as the canonical position end to end.

### Task 3 — Whole-robot calibration sequence (auto-squat starting pose, all 18 joints) → [TASK-3-WHOLE-ROBOT-CALIBRATION.md](TASK-3-WHOLE-ROBOT-CALIBRATION.md)
**~3 days (range 2.5–4).** Reuses Task 2 to calibrate the whole robot from any starting state. **Auto-squat pre-cal** drives every leg's hip to retract, knee to extend, and yaw forward then aft — recording hip-min / knee-max / yaw-min / yaw-max for all 6 legs as a side effect of reaching a deterministic pose. Then per-leg sub-sweep (rear-left → … → middle-right) captures knee-min + body-loaded hip-max. Per-board **serial numbers are passed as `--serials primary=…,left=…,right=…`** and written atomically with the cal block. No operator pre-pose required.

### Task 4 — Current-sense validation (final phase of calibrate-all) → [TASK-4-CURRENT-SENSE-AND-CAL-ERROR-HANDLING.md](TASK-4-CURRENT-SENSE-AND-CAL-ERROR-HANDLING.md)
**~2 days (range 1.5–3).** Runs as the final phase of `calibrate-all`, after Task 3's per-joint cal completes on all 18 joints: the firmware issues a neutral-pose command (every joint → position 0.5), then lifts the body half on each leg in turn and confirms current-sense reads near 0 unloaded and spikes (~2–8 / 1023) under load. Failures emit `ERR <joint> <code>` via Task 1 §5's error-telemetry channel; the SDK's `_FIX_INSTRUCTIONS` table turns the code into an operator-facing message. The per-leg lift is the **one M17 step that strictly needs the chassis** — `--skip-validation` skips it cleanly for bench-only runs.

### Task 5 — ZED 2i IMU through HAL into the model's body-frame state → [TASK-5-ZED-IMU.md](TASK-5-ZED-IMU.md)
**~1.5 days (range 1–2).** Add `ZedCamera.get_imu()` using pyzed's `Camera.get_sensors_data()` — the current `zed_camera.py` only exposes RGB + depth, so the IMU isn't reachable. Populate `HardwareObservations.base_ang_vel_b` and `base_quat_w` on every observation tick; apply a documented camera→body rotation; handle missing samples with rate-limited warnings + zero fallback. Verify end-to-end via the existing mapper's roll/pitch extraction (`compute/parkour/mappers/hardware_to_model.py` ~L131–141).

### Task 6 — HAL → model integration and flail test → [TASK-6-HAL-MODEL-INTEGRATION.md](TASK-6-HAL-MODEL-INTEGRATION.md)
**~2 days (range 1.5–3).** With Tasks 1–5 complete, run the default locomotion image with `--control-source inference` so the parkour model drives joints over HAL. Audit the mapper against the calibrated robot (joint positions in `[0,1]`, joint velocities computed Python-side, previous-action ranges agree). Decide the current-sense → `contact_forces` (5-slot, 6-leg) mapping and scale constants. Enumerate Isaac-only observation fields missing on real (the M15 randomization target list). Run for ≥ 30 s and capture the flail-test clip + HAL .mcap log.

### Cleanup / integration / slop (~3 days unassigned)
Headroom in the budget. Most likely places to absorb time: Task 1's primary↔follower debug; Task 4's chassis-dependent step (if the V0.2 chassis lands late, the per-leg lift validation slips into this window).

## FAQ
- **What's the firmware-code-quality bar?** **High.** Every firmware change in this milestone gets careful human review before merging — no AI-generated sprawl, no speculative abstractions, no "while I was in there" refactors. The bar:
  - **Minimal, human-readable extensions to existing features.** Read the surrounding code, match its style, add the smallest change that makes the test pass. New helper functions and abstractions need a clear, immediate use site — not a "we might need this later" justification.
  - **Function naming is held to a higher standard than the SDK side.** Names describe what the function does in the language of the existing firmware (e.g. `calibrateJoint`, `getRawPos`, `printTelemetry`, `forwardFullLines`), not vague verbs (`handle`, `process`, `manage`). No prefixes like `do_` or `_internal`; no Hungarian notation; no abbreviations the rest of the file doesn't already use.
  - **`.h` organization stays simple.** One concept per header — `eeprom_layout.h` for EEPROM struct, `hall_hw.h` for Hall hardware, `actuator_manager.h` for actuator/manager classes, `command.h` for command parsing. New work extends the right existing header or creates a new one only when a new concept genuinely needs it. No catch-all `utils.h`; no header-only abstractions added for symmetry.
  - **Serial interface definitions are the simplest thing that works.** Single-line ASCII, space-separated tokens, leading-token dispatch, no length prefixes, no binary framing, no per-command framing variations. The existing `T`/`B`/`J`/`C`/`H`/`V` pattern is the standard; new commands match it (see [Task 1 §4](TASK-1-V03-BRINGUP-AND-COMMS.md)). Wire-format changes are reviewed extra carefully because they're hard to walk back once binaries ship.
  - **Don't generate code from prompts and call it done.** Vibe-coded firmware is rejected at review. Every change is justified by a concrete need in the task spec; the contributor reads the result and can explain every line.
- **Is M17 a prerequisite for M15, or are they parallel?** Prerequisite. M15's Task 1 (parkour image bring-up on real robot) and Task 2 (joint mapping retrain) both assume the robot is calibrated and telemetry maps cleanly through HAL into the model. That's exactly what M17 delivers. M17 was scoped after M15 because the V0.3 board issues only surfaced once the M12 build was underway.
- **What about the V0.2 chassis — what's blocked on it?** Only Task 4's per-leg body lift strictly requires the chassis (you can't fake body load on a bench). **Tasks 0, 1, 2 can run entirely on bench hardware** — boards, motors, and a single detached leg are enough. **Tasks 3, 5, and 6 can also run bench-only** with the dynamics imagined (Task 3's auto-squat works against mechanical stops, not gravity; Task 5's ZED only needs the camera plugged into the Orin; Task 6's flail test confirms data flow, not gait). **The only real blocker is Task 4's current-sense lift.** Stay unblocked as long as humanly possible: the chassis is being built in parallel by another grantee and handed over partway through; if it doesn't land in time, Task 4's chassis-independent pieces (the error-code vocabulary in Task 1 §5, the `_FIX_INSTRUCTIONS` translation table, the `GET calibration` retrieval path) ship first and the live lift validation runs later — worst case mounted on a V0.1 chassis as a fallback.
- **Why isn't role auto-detected (USB-presence, SYNC handshake, etc.)?** Because explicit beats clever. The board's role is just a value in EEPROM, loaded on boot. The operator assigns it once with `SET role <PRIMARY|LEFT|RIGHT>` and it persists across reboots until the operator changes it. No auto-detect, no negotiation, no failure modes from a board guessing wrong. Operator plugs USB in, sends `SET role PRIMARY`, then uses the primary's `SET_LEFT` / `SET_RIGHT` to assign the followers' roles over Serial1/Serial2. Done.
- **How are per-board serial numbers set?** Same `SET` command as everything else: `SET serial <string>` writes to EEPROM. Serials and joint calibration are independent — the operator can assign serials whenever it's convenient, before or after `calibrate-all`. There's no atomicity contract between them.
- **Why the auto-squat starting pose instead of operator-set passive 90°?** Operator-set is fragile (the operator can be wrong about "mid-travel," and the robot might already be in a state the operator can't recover from manually). The auto-squat drives every joint to a known end-stop as its first action — the robot reaches the deterministic pose from any prior state, and recording the four end-stops is free as a side effect. Half the calibration is done before the per-leg sweep starts.
- **What's the deal with the "12 motors" vs 18?** Earlier framing said 12 (the linear actuators only). It's actually all 18 from the start — 12 linear + 6 hip-yaw. Task 0 wires all 18; Task 3's sequence calibrates all 18.
- **What about the MCU IMU from M16?** M16 will add a BMI270 on the MCU as the canonical body-frame IMU. M17 predates M16 in dependency order — M15 needs an IMU now, so M17 plumbs the **ZED 2i's onboard IMU** through HAL. When M16 lands, the BMI270 becomes the canonical source and the ZED IMU stays as a sanity check.
- **Can the dev redesign the calibration sequence if they find a cleaner one?** Yes — if you spot a sequence that avoids the foot-scraping or otherwise improves on what's in Task 3, go for it. **But the implementation has to stay composable from primitives** — `calibrateJoint(joint, direction=…)`, the directional substeps, and the pose-transition helpers (`moveJointTo`, `holdAll`). Don't replace it with a giant per-leg `if`/`switch` block of hardcoded moves. The hex calibration is going to be extended to other morphologies in the future (different leg counts, different actuator topologies), and we want the per-leg cal building blocks to be reusable. Net rule: any new whole-robot sequence is a *thin orchestration layer* over the Task 2 primitives, not a parallel implementation.
- **Does `isStalled()` already distinguish hitting an end stop from a real stall?** No, and it needs to be extended in Task 2. The existing `LinearActuator::isStalled()` (`actuator_manager.h` ~L169) only checks "motor commanded to move, position not changing for `timeout` ms" — that conflates two physically different states. The fix is to fold the current-sense reading (`avgIS`, already maintained per actuator at ~L46) into the check:
  - **End stop** — PWM applied + position not changing + `current ≈ 0` (the lead-screw clutch/limit has disengaged drive against the mechanical stop). **Normal.** This is what the Task 2 §6.5 self-heal logic anchors on (`sensor_min` / `sensor_max`) and what `calibrateJoint` uses to record the limits.
  - **True stall** — PWM applied + position not changing + `current high` (motor is fighting a jam, bind, obstruction, or driving against something un-stops-like). **Abnormal.** Emit `ERR <joint> motor_jammed` per Task 2 §2f, back off the PWM, and let the operator investigate.
  - Without the split, `calibrateJoint` could mistake a mid-stroke jam for an end stop (and record the wrong limit), and the self-heal logic could anchor a joint to the wrong absolute position. Task 2 extends `isStalled()` (or adds a sibling `endStopHit()` / `isJammed()`) so the two states are distinguishable by their current-sense signature.
- **How does the robot know absolute joint position across reboots without writing live state to EEPROM?** Each joint comes up in a `PARTIALLY_CALIBRATED` state — the firmware knows the full Hall range (`hallMax − hallMin`) from EEPROM cal constants but not the current absolute position on that scale. During normal motion, the first time the joint stalls against a known mechanical end-stop (`isStalled()` triggers while `currentPwm` is non-zero), the firmware snaps the signed Hall count to `hallMax` (extend stall) or `hallMin` (retract stall) and the joint transitions to `FULLY_CALIBRATED`. Anchoring one end implicitly fixes the other because the span is known. This self-heals during the first walking cycle that drives any joint to an extreme — no operator action, no boot-time homing dance, and **no live position written to EEPROM** (so no wear concern, and no risk of trusting a stale saved value across an unexpected reboot). See [Task 2 §6.5](TASK-2-PER-JOINT-CALIBRATION.md) for the full mechanism.
- **What about hip-yaw calibration once the V0.2 crank-and-slot mechanism lands?** The crank-and-slot yaw (per M12) has **no true mechanical end stops** — the motor rotates continuously while the leg sweeps ±30°. The Task 2 §6.5 self-heal-on-end-stop-contact mechanism can't anchor a continuously-rotating shaft. **A separate future milestone will handle that** — the planned approach is a **single-magnet sensor at the leg's "forward" position** (a Hall-effect sensor or reed switch detecting a magnet glued to the leg/crank at the chosen reference angle). On boot, the firmware rotates the motor slowly until the sensor trips, declaring that the absolute reference; from there the motor-side encoder count tracks position. For M17, the yaw motors are operated in a configuration that **does** have hard end-stops (whatever pre-crank mounting Task 0 lands on), so the Task 2 §6.5 mechanism applies to all 18 joints uniformly.
- **What does "current sense ≈ foot touch" mean for the model?** The model's `HardwareObservations.contact_forces` is a 5-entry vector originally trained against a quadruped force/torque-style sensor for foot-ground contact. On the real hex we proxy it from per-leg current draw — when a leg bears weight, its hip/knee actuators draw more current. Task 6 picks the actual current → 5-slot mapping; Task 4 just confirms the per-actuator signal is alive.
- **Where do per-board serial numbers come from?** Any scheme that's unique within the fleet (date-coded, fab-batch-coded, monotonic). `calibrate-all --serials primary=PRI-0042,…` writes whatever the operator provides. The fleet-side numbering policy is a separate decision.
