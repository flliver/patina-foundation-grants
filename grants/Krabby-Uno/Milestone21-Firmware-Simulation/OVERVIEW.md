# Patina Foundation Grant — Krabby-Uno Milestone 21: Firmware Simulation

## Grant Overview
Make the **entire Krabby Arduino firmware runnable in simulation** — no physical robot required — so that an AI or an engineer can exercise, test, and iterate on the firmware the same way they run any other part of the stack. Today the firmware only runs on the Arduino Mega: to see it do anything you must flash three boards, wire six actuators each, and watch a physical robot move, which is slow for a human and effectively impossible for an AI agent. This milestone closes that gap by building a **second implementation of the Arduino hardware API** — `digitalWrite`/`analogWrite`/`digitalRead`/`analogRead`/`millis`/`EEPROM`/`Serial`, and the hall-encoder interrupt path — that, instead of driving real pins, feeds **pin-level electrical values into IsaacSim** and reads simulated physics back out. The core abstraction is a `SimulatedRobotConfig` that composes a robot by binding every pin (from `firmware/arduino/board_pins.h`) to a defined actuator device, attached to a `RobotCore` game loop that watches pin transitions, finds the device on each pin, and executes the mapped Isaac command — so that `ActuatorManager::driveActuator()`'s `EN` + `PWM_R`/`PWM_L` writes turn into a linear actuator extending or retracting at the commanded speed. From that seam the milestone builds up: the read side — `digitalRead`/`analogRead`, EEPROM, the hall encoder, `millis`, plus a **physics-derived current-sense** signal that rises as a foot loads the ground; then the serial command/telemetry protocol so the existing **krabby-SDK** can drive the simulated firmware and read telemetry back, and the inter-board serial links so all **three simulated Arduinos control all 18 legs** in one IsaacSim scene; simulators for the **M16 I2C sensors** (IMU, OLED health screen, battery monitor); and finally a **third HAL implementation** (`FullSimulator`) that puts krabby-SDK *and* the firmware in the call path for a normal image launch, so a simulated krab can register with the fleet manager and be teleoperated. The output is a firmware you can run, drive, and observe entirely in software.

## Why is this Important?
- **The firmware is currently untestable without hardware.** Every firmware change today requires flashing physical boards and watching a real robot — no CI signal, no AI-in-the-loop, no reproducible test. This milestone makes the firmware a normal, runnable, testable software component.
- **It unblocks AI-driven firmware development.** An agent can define a simulated robot, send commands, and *see* each leg move via unit tests — impossible with the flash-and-watch loop today.
- **It closes the last un-simulated layer of the stack.** The HAL already has an Isaac backend, but that backend *bypasses* the firmware and krabby-SDK entirely. After M21 the real firmware control loop and serial protocol run in the simulated call path, so what you test in sim is what ships on the robot.
- **It gives current-sense (and the health UI) something real to show.** A physics-backed current signal that responds to ground contact makes the GUI and telemetry meaningful in sim, and gives us a tunable foundation for contact-based behaviors in later milestones.
- **It is the foundation for fleet-level simulation (M23).** Once the firmware runs in sim behind the HAL, a simulated krab can be pulled, launched, and teleoperated through the fleet manager on a desktop GPU box — the M23 goal — with M21 having proven the base emulator works reliably.

### Task 1 - RobotCore loop + digitalWrite: drive the actuators → [TASK-1-PIN-SIMULATION-INTERFACE.md](TASK-1-PIN-SIMULATION-INTERFACE.md)
#### Narrative
Build **just two things**: the `RobotCore` game loop and the **output** pin calls (`pinMode`/`digitalWrite`/`analogWrite`, plus `millis` for the loop clock). When the firmware's `driveActuator()` sets `EN` high and a `PWM_R`/`PWM_L` duty, the sim records those writes and the `RobotCore` loop resolves the actuator device on those pins and drives the linked IsaacSim joint at the signed, proportional speed (`(EN==HIGH) × (PWM_R − PWM_L)`, −255…255, linear: `−255` = full retract, `+122` = ~48% extend). The deliverable is a `RobotCore` you can **jog** — drive each of the 6 legs open-loop from test code and watch the joint move in sim.

Nothing on the **read** side is in Task 1. `analogRead` (pot position, current-sense) and `digitalRead` are **stubbed** here and implemented in Task 2 — so there is deliberately no position feedback, no closed-loop P-controller, and no calibration in Task 1; those all depend on reads and belong to Task 2. This task also stands up the minimal host build that does not exist today — enough to compile the drive path (`driveActuator`/`manualDrive`) against a pin-output + `millis` shim; hall, EEPROM, and serial are stubbed. Scope: `SimulatedRobotConfig` + `SimulatedActuator` + `RobotCore`, one board, 6 motors, `KRABBY_PIN_REV` 3. Verified by unit tests that jog each leg and assert the Isaac joint moves, checked by inspecting the sim joint directly (there is no `analogRead` yet).
#### Acceptance Criteria
- **1a** — The firmware's actuator **drive path** (`driveActuator`/`manualDrive`) compiles and runs on the host against a **minimal output shim** (`pinMode`/`digitalWrite`/`analogWrite`/`millis`). `analogRead`/`digitalRead` and the system calls (hall, EEPROM, serial) are **stubbed** here — implemented in Tasks 2–3. The existing `arduino-cli` AVR build (`firmware/Makefile`) still works unchanged.
- **1b** — A `SimulatedRobotConfig` binds each of the 6 slots' **drive pins** (PWM_R/PWM_L/EN, per `board_pins.h` for **`KRABBY_PIN_REV` 3** — the only revision the emulator must support) to a `SimulatedActuator` bound to a named IsaacSim joint. (POT/IS pins are declared in the config but only read in Task 2.)
- **1c** — A `RobotCore` accepts a `SimulatedRobotConfig`, runs a game loop, and on each tick reads the recorded pin state, resolves the device owning each pin, drives the linked joint, and steps physics.
- **1d** — `driveActuator()`'s pin writes map to a **signed motor command** `cmd = (EN==HIGH) ? (pwm_R − pwm_L) : 0` (from the recorded `digitalWrite`/`analogWrite` state), range −255…255: `−255` retracts at 100% speed, `+255` extends at 100%, `+122` extends at ~48%, `0`/EN-low holds. Assume **linear** dynamics.
- **1e** — The 6 motors are independently addressable: driving one leg moves only that leg's joint; the pin→device→joint resolution is correct for all six slots.
- **1f** — Integ tests jog each of the 6 legs (extend, retract, hold, partial-speed) and assert the linked Isaac joint moves in the right direction at the right proportional speed — verified by inspecting the sim joint directly.

### Task 2 - digitalRead / analogRead: sensors and current-sense → [TASK-2-SENSORS-AND-CURRENT-SENSE.md](TASK-2-SENSORS-AND-CURRENT-SENSE.md)
#### Narrative
Build the **input/read side** — `analogRead` and `digitalRead` — on top of Task 1's drive loop. The first read is `analogRead(pinPot)`: it returns each joint's position on the ADC scale, which **closes the firmware's control loop** — `getPos()`, the `update()` P-controller (position targets via `setTarget`), and the auto-calibration state machine all start working, none of which existed in Task 1 (which drove open-loop only). Each motor's pot also carries **per-motor calibration variance** (deterministic but drawn at `SimulatedRobotConfig` instantiation from a min-stop range ~80–220 and max-stop ~800–1000, mimicking manufacturer POT variance), so auto-calibration discovers different limits per motor. `digitalRead(pinEn)` gives the EN read-back; the hall edge counter is a native shim that emulates `saf` from joint motion, scaled so a full min→max travel matches the real robot's triggers-per-travel (from James, or read off a real robot via the fleet manager); `EEPROM` is a byte array (in-memory is fine at this stage) for `CalData` + role; `millis()` is a monotonic sim clock.

The headline deliverable is a **current-sense signal derived from IsaacSim physics**. `analogRead(pinIS)` is mapped from the joint reaction wrench (`robot.data.body_incoming_joint_wrench_b`) at the appropriate leg link — resolved via `robot.find_bodies()` — with the per-joint actuator `applied_effort` as a cheaper cross-check. The value is tuned low and by eye: **0** no movement, **~2** moving without ground contact, **4** basic ground contact, scaling to **~30 of 1023** when a leg lifts significant force (offloading the other legs). Validation here is unit tests plus a manual tuning harness (a windowed single-env viewer where you perturb a leg and watch the wrench) — both read the sim directly. Physical accuracy is explicitly not the goal here — sensible, tunable outputs are; fidelity is a later milestone.
#### Acceptance Criteria
- **2a** — `digitalRead(pin)` returns the last state written to that pin (EN lines read back correctly for the telemetry `enL`/`enR` fields Task 3 emits).
- **2b** — `analogRead(pinPot)` returns each joint's position on the ADC scale, **closing the control loop**: `getPos()`, the `update()` P-controller (via `setTarget`), and auto-calibration all now work — none existed in Task 1 (open-loop only). Each motor's readout also carries per-motor **calibration variance**: deterministic but assigned at `SimulatedRobotConfig` instantiation — min-stop drawn from ~[80,220], max-stop from ~[800,1000], fixed per motor thereafter (seeded from the config so it's reproducible) — so auto-calibration discovers a different `minStop`/`maxStop` per motor, mirroring real manufacturer POT variance. (This is where `RobotCore`'s loop gains its read path — it now also reads joint positions back to feed the pots, which Task 1 left open.)
- **2c** — `EEPROM.put`/`get`/`read`/`update` are backed by a byte array; the calibration `CalData` (byte 0, magic `0xDEADBEEF`) and board role (byte 32 magic `0xAB`, byte 33 role) round-trip properly. Note, there's no need for a 'between reboots' mechanism at this stage, in memory is fine.
- **2d** — The hall edge counter (`hallHwInit`/`hallHwGetEdgeCount`) is a native shim that **emulates edge counts from simulated joint velocity** (no AVR register/ISR emulation); `saf` advances monotonically as a joint moves and holds when it stops, and the **total count across a full min-stop→max-stop travel matches the real robot** — obtain the average encoder triggers between stops from James, or read them off a real robot via the fleet manager.
- **2e** — Task 2 completes the **read + timing** Arduino surface the actuator/sensor layer needs on top of Task 1's output shim: sweep `actuator_manager.h`/`hall_hw.cpp` for any remaining Arduino symbol (`analogRead`, `digitalRead`, `EEPROM`, the hall counter; `millis` already comes from Task 1's shim) and give each a sim impl, so the simulated actuator+sensor layer imports no real Arduino. (`Serial` is Task 3 and `Wire`/I2C is Task 4 — the only Arduino APIs left after Task 2.)
- **2f** — `analogRead(pinIS)` returns a **physics-derived** current value: hook `robot.find_bodies()` + the joint reaction wrench (`body_incoming_joint_wrench_b`) at the appropriate leg link (knee/hip), mapped onto the 0–1023 ADC scale.
- **2g** — The current-sense scale is tuned to: **0** = no movement, **~2** = moving without ground contact, **4** = basic ground contact, scaling to **~30 of 1023** when a leg lifts significant force (starting to pick up the body / offload other legs). Behavior is changeable by modifying output mapping function.
- **2h** — `Current-sense, POT, and hall values are validated via integ tests` Move a leg via direct PWM pin commands, show the POT/hall/current value changes as expected by round tripping through isaac SIM.
#### Time estimate (~6 days)
| Days | Sub-task title |
|------|----------------|
| 1 | `analogRead(pinPot)` position read (closes the control loop) + `digitalRead` EN read-back |
| 0.5 | Per-motor pot calibration variance + EEPROM (`CalData`/role, in-memory) |
| 1 | Hall edge synthesis (scaled to James's real-robot triggers-per-travel) + confirm `millis`/timing tracks sim time |
| 2 | Physics current-sense: wrench (`body_incoming_joint_wrench_b`) → `pinIS`; manual tuning harness; tune 0 / ~2 / 4 / ~30 |
| 0.5 | Integ tests (pot read + variance, digitalRead, EEPROM, hall + travel count, millis, current-sense breakpoints) |

### Task 3 - Serial emulation and three-board firmware → [TASK-3-SERIAL-EMULATION.md](TASK-3-SERIAL-EMULATION.md)
#### Narrative
Extend the simulated firmware to speak the **serial protocol** end to end, so the existing **krabby-SDK** (`firmware/krabby_mcu.py`) can connect to the simulated MCU, send commands, and receive telemetry back — closing the full command → motion → telemetry loop against IsaacSim. Because the SDK opens a port by path and honors `KRABBY_MCU_PORT`, the simulated MCU attaches through a virtual serial device (a PTY, or a virtual COM pair on Windows) with **no SDK changes**. The simulated firmware parses the full host→MCU command set (`T` targets, `B` batch jog, `J` single jog, `C` calibrate, `H` hold, `V` version) and emits role-prefixed telemetry lines in the exact wire format on the ~50 ms tick. Since Tasks 1–2 already produce real drive + sensor values, wiring serial makes them flow to the SDK — so the **`python -m firmware.gui` should work as is: move the robot, watch the "Cur"/"Pot" column respond.

This task then emulates the **inter-board serial links** so **three** simulated Arduinos cooperate in one IsaacSim scene, driving all **18 legs**. It includes wiring each emulator instance's `Serial1`/`Serial2` to its peers so the real `determineRole()` election runs (one FRONT leader, LEFT/RIGHT followers), the leader forwarding each follower's telemetry line verbatim and relaying commands, and binding the three boards to three disjoint sets of six joints of the shared crab Articulation. A single-leader shortcut (one emulator owning all 18 joints, emitting all three role-prefixed lines) is a valid stepping stone before the true three-instance election exercises the multi-board code paths.
#### Acceptance Criteria
- **3a** — The simulated firmware exposes a serial endpoint that `serial.Serial(port)` can open by path; `KrabbyMCUSDK(port=...)` / `KRABBY_MCU_PORT` connects with **no SDK code changes**.
- **3b** — The simulated firmware parses the full host→MCU command set: `T` (position targets, val 0–1), `B` (batch jog, pwm −255…255), `J` (single jog), `C` (calibrate), `H` (hold/de-energize), `V` (version) — matching `arduino.ino`'s `loop()` dispatch.
- **3c** — The simulated firmware emits telemetry lines in the exact wire format every ~50 ms: `<ROLE>; <name> <pos> <pot> <current> <enL> <enR> <pwmL> <pwmR> <saf>; …` (6 joints per line, `;`-joined), parseable by `firmware/interfaces/joint_telemetry.py` unchanged.
- **3d** — A full round trip is demonstrated: SDK sends a jog/target command → the linked Isaac joint moves → telemetry reflects the new `pos`/`pwm`/`en` → `KrabbyMCUSDK.joints[name]` updates. All in a unit/integration test, no hardware.
- **3e** — `V` (version) returns a well-formed `VER …` reply that `parse_ver_reply` accepts; `H` de-energizes all actuators; `C` starts the calibration state machine and completes against simulated joint limits.
- **3f** — Three simulated Arduinos elect roles (one FRONT leader, LEFT and RIGHT followers) over emulated inter-board serial, matching `determineRole()` semantics, and the leader ends up owning the USB/host link.
- **3g** — The leader forwards each follower's full telemetry line verbatim to the host, so the SDK sees three role-prefixed lines (`FRONT;…`, `LEFT ;…`, `RIGHT;…`) per cycle, and relays `T`/`B`/`J`/`C`/`H`/`V` to followers.
- **3h** — The three MCU instances are each bound to a disjoint set of 6 joints of the same 18-joint crab in one IsaacSim scene; commanding any of the 18 legs through the SDK moves exactly that leg.
- **3i** — End-to-end current-sense in the GUI: `python -m firmware.gui` against the simulated MCU shows the "Cur" column responding as legs load the ground (rise on contact, ~30 when lifting the body, ~0 at rest) — the payoff of Task 2's current-sense over this task's serial — and serial telemetry stays nominal (all fields parse via `joint_telemetry.py`).
#### Time estimate (~7 days)
| Days | Sub-task title |
|------|----------------|
| 1.5 | Simulated `Serial`/`HardwareSerial` backed by a virtual serial device; SDK connects via `KRABBY_MCU_PORT`/PTY |
| 0.5 | Host→MCU command parse (`T`/`B`/`J`/`C`/`H`/`V`); telemetry emitted in exact wire format on the 50 ms tick |
| 0.5 | Full round-trip test: command → Isaac motion → telemetry → `mcu.joints[...]`; `V`/`H`/`C` behaviors |
| 1.5 | Three-instance role election over emulated inter-board serial; leader telemetry forwarding + command relay |
| 1 | Bind three boards to 18 joints in one scene; per-leg addressability test across all 18 |
| 0.5 | GUI current-sense end-to-end (`python -m firmware.gui`) + telemetry-nominal check |

### Task 4 - I2C sensor simulators (IMU, OLED, battery) → [TASK-4-I2C-SENSOR-SIMULATORS.md](TASK-4-I2C-SENSOR-SIMULATORS.md)
#### Narrative
Add simulators for the **Milestone 16** I2C sensors — a simulated **IMU** (BMI270, `0x68`), the **OLED health screen** (SSD1306, `0x3D`), and the **battery-sense chips** (two INA228, `0x40`/`0x41`). This task **adds the simulated `Wire`/I2C layer** on top of the Task 1 host build (Task 1 built the pin/`millis` shim; there is no `Wire` yet). All three are I2C with standard call/response patterns, so the sim mimics the data already present in M16's unit/integration tests rather than modeling any physics: the simulated `Wire` layer returns believable register values and the *real* driver code (compiled in the host build) does the parsing. The IMU can derive accel/gyro cheaply from the sim base state; the INA228s return a nominal pack/per-battery reading; the OLED simulator (John's) is hooked through the simulated `Wire` interface so it renders the krab status screen from live simulated-firmware state. This is a short task requiring little simulation integration or dynamics.

**Two dependencies must be resolved first, and the task flags them explicitly:** (1) the **M16 sensors are not yet implemented in the real firmware** — there is no `sensors_config.h`, no `#include <Wire.h>`, and no BMI270/SSD1306/INA228 code in `firmware/arduino/` today; M16 is spec-complete but code-incomplete. (2) **John's OLED simulator is not committed to `krabby-research`** — it must be located and vendored in (or pointed to). If the M16 firmware is incomplete when this task starts, the sim work proceeds against the same agreed I2C contract (addresses + `IMU`/`BATT` telemetry schemas) the M16 grant already specifies.
#### Acceptance Criteria
- **4a** — A simulated I2C/`Wire` layer supports the four M16 device addresses (BMI270 `0x68`, OLED `0x3D`, Pack INA228 `0x40`, Midpoint INA228 `0x41`) with standard read/write call/response; addressing an absent device fails gracefully (matching the firmware's init-failure handling).
- **4b** — The simulated IMU returns accel (3-axis), gyro (3-axis), and temperature; the simulated firmware appends the M16 `IMU` telemetry segment and `joint_telemetry.py`'s IMU parser (from M16) accepts it.
- **4c** — The OLED simulator is driven through the new pin/`Wire` interface and renders the health screen (controller-thirds liveness, per-actuator glyphs, battery bars) from the simulated firmware's live state — not a standalone mock.
- **4d** — The simulated INA228s return pack + per-battery voltage/current; the simulated firmware emits the M16 `BATT` frame; the M16 battery parser accepts it.
- **4e** — Sensor values mirror the data already present in M16's unit/integration tests (no new physics); where a value can be derived cheaply from the sim (e.g. IMU from base orientation/velocity), it may be, but fidelity is not required.
- **4f** — Tests exercise each simulated sensor end-to-end through the firmware (I2C call → firmware read → telemetry/OLED output), with no hardware.
- **4g** — Absent/failed sensors do not crash the simulated firmware (init failure sets the invalid flag and control continues), matching M16's non-fatal-init requirement.

### Task 5 - HAL `FullSimulator` backend and fleet integration → [TASK-5-HAL-FULLSIMULATOR.md](TASK-5-HAL-FULLSIMULATOR.md)
#### Narrative
Rewire the HAL to add a **third implementation** alongside the existing Jetson ("Krabby") and Isaac backends: a **`FullSimulator`** server that loads and executes the *entire firmware layer* in the call path — krabby-SDK → simulated firmware → simulated pins → IsaacSim — replacing today's Isaac backend that converts a `JointCommand` straight into joint position targets and never touches the firmware. `FullSimulator` reuses the Isaac observation half (subclassing `IsaacSimHalServer` so `set_observation`/`_cache_references`/the sensor interface are unchanged) and overrides only the command path: a `JointCommand` is converted to firmware commands (radians → normalized, as the Jetson adapter does), the simulated firmware's `ActuatorManager` control loop runs, its simulated pins produce per-joint drive, and that becomes the `env.step` action tensor (the same shape today's Isaac `apply_command` returns). The backend is selected the way the others are — a `krabby-hal-server-fullsim` console script and/or a `--backend fullsim` flag in the sim launcher.

This task then demonstrates, via an integration test, that the image can be spun up, the simulator launched through the new interface, and the simulated krab **registered with the fleet manager and teleoperated**, reusing the existing teleop signaling. Because this is an untested path — the fleet/teleop stack has never run against a firmware-in-the-loop simulator — the task expects to surface and fix a few missing pieces (or clearly document them as M23). Heavy fleet productization (publishing a sim image to ECR/S3, "no krab attached → pull SIM image" auto-detect, GPU validation, IoT resume) is explicitly **out of scope and deferred to M23**; Task 5 proves the path works, it does not productize it.
#### Acceptance Criteria
- **5a** — A `FullSimulatorHalServer(HalServerBase)` exists in `hal/server/fullsim/` and implements the practical HAL contract: `set_observation(self)` building a valid `HardwareObservations` and calling `super().set_observation(...)`; a command path that consumes a `JointCommand`; `get_sensor_interface()`; and `close()`.
- **5b** — The command path puts **both krabby-SDK and the firmware in the loop**: a `JointCommand` is converted to firmware commands (radians → normalized, as the Jetson adapter does), the simulated firmware's `ActuatorManager` control loop runs, its simulated pins produce per-joint drive, and that becomes the `env.step` action tensor — replacing the direct `JointCommand`→position-target passthrough of `IsaacSimMCUSDK`.
- **5c** — Observations still come from the Isaac env (joint state, base state, cameras, contacts), reusing `IsaacSimHalServer.set_observation`/`_cache_references` so the observation half is unchanged.
- **5d** — The backend can be selected and launched: a `krabby-hal-server-fullsim` console script (or a `--backend fullsim` flag in the sim `main.py`) constructs and runs the new server; existing Jetson/Isaac launches are unaffected.
- **5e** — An integration test spins up the simulator through the new interface and drives the full path end to end (command in → firmware loop → sim pins → `env.step` → observation out), asserting a teleop command moves the simulated robot and observations reflect it.
- **5f** — The simulated krab **registers with the fleet manager**, appears in the UI, can be connected to, and is teleoperable; when the sim is stopped it shows offline (manual restart via the krabby CLI — no IoT resume).
- **5g** — Any missing pieces on this untested path are identified and fixed (or clearly documented as deferred to M23), since the fleet/teleop path has not been exercised against the firmware-in-the-loop simulator before.
#### Time estimate (~5 days)
| Days | Sub-task title |
|------|----------------|
| 1 | `hal/server/fullsim/` package scaffold: `FullSimulatorHalServer` reusing Isaac observation half; console script + `pyproject.toml` |
| 1.5 | Command path: JointCommand → firmware control loop → simulated pins → `env.step` action tensor |
| 0.5 | Backend selection (`--backend fullsim` / console script); confirm Jetson/Isaac launches unaffected |
| 1 | Integration test: full path end-to-end, teleop command moves the sim robot |
| 1 | Fleet registration + teleop demo; enumerate/fix gaps or document M23 hand-offs |

## Looking ahead to M23
M21 delivers a reliable base emulator: the firmware runs in sim, krabby-SDK drives it, and a `FullSimulator` HAL backend puts it in the normal image call path. **M23** builds the fleet-manager experience on top: install the krabby fleet client on a stock Ubuntu box, have it detect that no real krab is attached (the `mcu_present` signal already exists in `krabby/telemetry.py`), prompt to pull an **IsaacSim image instead of the real image** (which requires standing up a `publish-isaacsim` workflow + ECR repo — the sim image builds locally today but is never published), validate the box has the GPU to run it, launch it, and have it register with and be teleoperated through the fleet manager UI. When the sim is off, the robot shows offline until manually restarted via the krabby CLI (no IoT-based resume yet). None of that is in M21 scope; it is captured here so the emulator work lands with the fleet direction in view.

## FAQ
- **Why a second `digitalWrite`/`analogWrite` instead of rewriting the firmware for sim?** The whole point is to run the *real* firmware — the same `actuator_manager.h` control loop, ramp, deadbands, and serial protocol that ship on the robot. Swapping the hardware API underneath (not the control logic) means what you test in sim is the shipping firmware, not a reimplementation that can drift.
- **How does a PWM value become motion?** `driveActuator()` writes `EN` HIGH/LOW and one of `PWM_R`/`PWM_L` (0–255). The simulator reads those pins as a signed command `(EN==HIGH) ? (pwm_R − pwm_L) : 0` in the range −255…255 and drives the linked Isaac joint at the proportional speed (assume linear dynamics for now). Position feedback comes back as `analogRead(pinPot)` mapped to 0–1023.
- **Does the firmware compile off the Arduino today?** No. It only builds for AVR via `arduino-cli`, and there is no C++ unit-test harness anywhere in the repo. Task 1 stands up only a **minimal** host shim (pin I/O + `millis`) sufficient to compile and run the actuator control layer (`actuator_manager.h`); it does **not** emulate any AVR machinery. The fuller host build — the AVR-specific `hall_hw.cpp` and EEPROM (Task 2) and serial (Task 3) — is filled in as those subsystems come online, so no task is "emulating AVR" ahead of when that subsystem is actually implemented.
- **Which board revision does the emulator support?** Only **`KRABBY_PIN_REV` 3** (the current Uno v0.2 board). It does not need to handle Rev 1/2. Supporting a future pin revision should be cheap: update the pin numbers in `firmware/arduino/board_pins.h` (as you would for the real firmware anyway), then update the emulator's `SimulatedRobotConfig` to map the new/changed pin to its `SimulatedActuator`. No emulator-core changes — the pin→device→joint resolution is data-driven from the config, so a pin move is a one-line binding change, not a code change.
- **Do we need real serial ports for the SDK to talk to sim?** No. `KrabbyMCUSDK` opens a port by *path* and honors `KRABBY_MCU_PORT`, so the simulated MCU attaches through a virtual serial device (a PTY, or a virtual COM pair on Windows) with zero SDK changes.
- **Is the current-sense meant to be physically accurate?** No — explicitly not at this stage. The goal is *sensible, tunable* outputs (0 / ~2 / 4 / ~30 of 1023 across no-motion → loaded-contact) that respond correctly to what the robot is doing. Fidelity is a later milestone.
- **Where does the current-sense number actually come from?** IsaacSim physics: `robot.data.body_incoming_joint_wrench_b` (the joint reaction wrench through the leg) at the hip/knee, resolved via `robot.find_bodies()`, mapped down onto the `pinIS` 0–1023 ADC scale. The per-joint actuator `applied_effort` is a cheaper secondary proxy.
- **Why is Task 4 "short" when M16 was a whole milestone?** Task 4 only simulates the I2C call/response for three sensors behind the pin interface built in Tasks 1–3 — no physics, no dynamics. It mirrors data already in M16's tests. (It *does* depend on the M16 firmware and John's OLED simulator existing, which the task calls out.)
- **What is the difference between the existing Isaac HAL backend and the new `FullSimulator`?** Today's Isaac backend converts a `JointCommand` straight into Isaac joint position targets — the firmware and krabby-SDK are *not* involved. `FullSimulator` keeps the Isaac observation half but routes commands through krabby-SDK → the simulated firmware → simulated pins → the env action, so the real firmware control loop is exercised end-to-end.
- **What's deferred to M23?** The full fleet-manager experience — publishing a sim image to ECR/S3, auto-detecting "no krab attached → pull the SIM image," and making the whole system simple to use. M21 focuses on getting the base emulator working reliably; Task 5 proves the path end-to-end but heavy fleet wiring is M23. (See "Looking ahead to M23" above.)
