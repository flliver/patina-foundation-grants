ok, we're going to work on the Milestone21-Fleet-Simulation milestone now.


Task 1, is taking on some core work now of the milestone as a whole. The milestone as a whole is attempting to make it so that AI or engineer can run the full krab firmware in a simulated manner. Right now the firmware runs only on Arduino, so it makes it difficult to test the firmware, because you have to install it on a physical robot and watch it do the things, something an AI can't do (easily). Instead, what we'll do in this task is write an interface to isaacSim (or really any SIM), where it accepts PIN level simulated electrical values, then the interface impl turns those pin level values into appropriate signals in simulation. These pins are all defined in firmware/arduino/board_pins.h, and are used mostly inside ActuatorManager.h::driveActuator, which calls digital/analogWrite to the appropriate PINs. What we need to do is make a second implementation of digital/analogWrite that calls into IsaacSim instead of the Arduino hardware, and has an internal game loop and state machine that executes appropriate actoins based on the active pins. In the case of the driveActuator, what should happen is that when EN is up and PWM is set to a value from -255..255, it should drive the appropriate linear actuator for that pin at that speed. i.e. -255 should retract at 100% speed, 122 should extend at slightly under 50% speed. For now assume the motor has linear dynamics (though I doubt it does in real life, but that's for a later test). The core of this module should be a 'SimulatedRobotConfig', which composes a robot by assigning all pins to defined actuators, where each actuator is probably it's own class that requires the PIN definition + IsaacObject or whatever definition. The the RobotCore or whatever, is using its game loop to listen to pin flips, finding the appropriate device linked to that pin, then executing the appropriate mapped Isaac command(s) based on the pin values.

This task #1 is to get this working just with one emulated arduino with 6 motors, show that you can define a SimulatedRobotConfig, attach the config to a RobotCore instance, then you can via unit tests call into this simulated robot and see each of the legs move like they are supposed to.

This will require emulating the serial interface that emits telemetry, as well as communicates commands back to Krabby-SDK. It will also require instantiating each instance of the arduino emulator to hook to three different sets of joints in the same IsaacSim simulation.

Task 3 now, you extend the simulated interface to include all the digitalRead(), eeprom, the HW interrupt handler used by the hall encoder, and any basic stuff like millis() or other system level functions. You write unit tests for everything, so that you can now get the current sense to show some values when the robot foot hits the floor, based on the pressure the robot hits the floor. This should be tuned very low, 0 for no movement, ~2 for movement without contact, 4 for basic ground contact, scaling to ~30 (of 1023) for ground contact where the leg is lifting significant force (i.e. is starting to pick up the body and remove weight from the other legs). This will require hooking into isaacSim's physics engine, into the already existing implementations we have (i.e. robot.find_bodies() to get the joints, then extracting leg force from the knee or hip joint as appropriate using the joint wrench values), then mapping down to appropriate values. This is best done manually by viewing the robot, manually moving the leg, then seeing the force on the leg. The output of this task is that in the standard viewer(s) i.e. 'python -m firmware.gui' being the most basic, that you can see appropriate current sensing as you move the robot in simulation. NOte, at this phase we don't particularly care that it's completely accurately reproducing the dynamics and behavior, we just care that we are seeing normal and sensible outputs from the simulation, pin interfaces, etc. that we can then tune in a later milestone as appropriate. In addition to python -m firmware.gui working, you should also validate that the serial telemetry output from the firmware looks nominal, i.e. it still properly spits out joint positions and the like.

Some appendix information for the next milestone (M23). M21 should focus on getting the base emulator working reliably, M23 will focus on making all of the whole system with the fleet manager and everything above it all comes together and is really simple/clear to use.


The goal of this milestone is to make it so that through the fleet manager, you can run a simulated krab inside isaacSIM on a 5080 or equivalent desktop. That means that we need to be able to install the krabby fleet client on a regular ubuntu box, then have it recognize that it's not attached to a real krab and to have it pull down the isaacSim image instead of the real image. Then it should start the isaacSim image, properly initialize the hal to talk to Krab in sim, and make sure all the existing work to have the image register with the fleetm anager still works with the sim. This is task 1, because all this stuff should already be working from earlier milestones, but is currently untested, and I think the isaac image is probably not publishing to S3/ECR.

I would like you to read all the image code in krabby-research though, as well as the fleet dir and review the way the fleet cli works to list out any changes that might need to be made to support doing what's staetd above. At the very least, the fleet CLI and maybe the main krabby CLI in the krabby dir might need to be tweaked to support pulling the isaac image instead of the regular image, as well as figure out and/or prompt user that the krab is not attached and see if they want to install a SIM image (after validating that the box they are running on has the HW needed to run the sim image).

At the end of task 1, you should be able to now register and run a krab inside the fleet manager UI, see it on the UI, connect to it, and teleoperate the simulated robot via the fleet manager. Again, this is a single task (~20 hours) because all of this image level stuff is already working well from previous milestones, and the sim image is already working from previous milestones. When the Sim is turned off on the box, it should show offline on the fleet manager, requiring you to manually turn on the SIM again via the appropriate krabby cli call. It does not yet need to have some sort of fleet based resume via IOT, as that would need to be a new feature.
