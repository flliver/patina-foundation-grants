# Task 1 – Firmware Store and `krabby-firmware` CLI

## 1. Narrative

Move firmware binaries out of the Python wheel and into a public S3 bucket organized by branch. CI builds an Arduino HEX file on every commit and uploads it. The `krabby-firmware` PyPI package becomes a thin client over the bucket plus a flash tool: list available builds, pick a version, flash a Mega.

The Arduino sketch today has no version reporting (no `__DATE__`, no `VERSION` macro, no serial query). Add a `V` command on the main serial that returns branch + commit + version, populated from a `version.h` generated by CI. Without this, `krabby-firmware --show` cannot tell the user what is currently flashed; the bootloader can identify the chip but not the application, and the USB iSerial is hardware-fixed.

## 2. Scope

- **S3 bucket (new, public-read):** `s3://krabby-firmware-public/` (or equivalent). Layout: `<branch>/<commit-date-time>-<commit sha>/firmware.hex` + `manifest.json`. Branch names mirror Git: `mainline`, `release/0.2.x`, etc.
- **CI workflow:** On push to mainline or `release/*`, generate `firmware/arduino/version.h` (see Firmware change below), build the HEX with `arduino-cli` against a pinned core version, write the manifest, upload to S3, update `<branch>/latest.json` and `index.json`. Check existing github repo for how current wheel publishes work and extend to work with AWS S3 write instead of pypi publish.
- **Firmware change:** Generated `firmware/arduino/version.h` defines `KRABBY_FW_VERSION`, `KRABBY_FW_BRANCH`, `KRABBY_FW_COMMIT` (defaulting to `dev-local` when not generated). Add a `V` case to the command switch in `arduino.ino loop()` (alongside `T`/`B`/`J`/`C`/`H`) that prints `VER <version> <branch> <commit-short>` on `mainSerial`. Each board answers on its own main serial; the leader combines all versions and returns final version string, e.g. "VER -|1.0|1.0 mainline|release/1.0|release/1.0 2389AD|dk3A34F|l3ifjr", always as 'primary|left|right'
- **`krabby-firmware` CLI** (existing entry point in `firmware/pyproject.toml`):
  - `--install`: one-time host system setup so Mega serial ports are usable without sudo. Writes a udev rule for the Mega 2560 (so `/dev/ttyACM*` has accessible perms), ensures the invoking user is in `dialout`, and installs `avrdude`/`arduino-cli` on the host if missing. Idempotent. Required only when running `krabby-firmware` standalone on the host; if going through the locomotion image (Task 2 bundles the flash tools), `krabby --install` performs the equivalent host setup.
  - `--show`: lists attached Krabby boards (port, USB ids, version reported via `V`) and the available branches/builds in the bucket.
  - `--update [<port>]`: flashes the latest build from the latest non-mainline branch (most recent `release/*`).
  - `--update <branch> [<port>]`: flashes the latest build from the named branch (`mainline` is valid).
  - Caches downloads under `~/.cache/krabby-firmware/<branch>/<commit>/`.
- **Python SDK:** `KrabbyMCUSDK.read_version(timeout=...)` sends `V\n` and parses the reply line.
- **Flash backend:** `avrdude` (or `arduino-cli upload`) against the Mega 2560. Installable on the host via `krabby-firmware --install`; also bundled into the locomotion image (Task 2) so a user who only `pip install krabby` can flash from inside the container without any extra host install.

## 3. Acceptance Criteria

1. Public S3 bucket exists with the documented branch-per-directory layout
2. CI publishes a new build to S3 on every push to a tracked branch; manifest carries branch + commit + the `VER` string the firmware reports.
3. The Arduino sketch answers `V\n` with `VER <version> <branch> <commit-short>` on the main serial, properly handling version forward/combining primary/secondary boards.
4. `pip install krabby-firmware` on a clean Linux venv gives a working CLI; the wheel contains no firmware binary.
5. `krabby-firmware --show` lists attached boards (port + version) and the bucket's branches/builds.
6. `krabby-firmware --update` (no branch) flashes the latest build from the latest non-mainline branch.
7. `krabby-firmware --update <branch>` flashes the latest build from the named branch, including `mainline`.
8. `firmware/SETUP.md` documents the bucket layout, the `V` protocol, the three-board update procedure, and other documentation as needed.
9. `krabby-firmware --install` is idempotent and sets up host udev rules, `dialout` membership, and flash tool dependencies (`avrdude` / `arduino-cli`) so subsequent `--update` calls work without sudo.
10. Local unit tests cover S3 manifest parsing, branch + "latest non-mainline" selection logic, the `version.h` template generator (golden test), the VER serial-reply parser in `KrabbyMCUSDK.read_version` (against fake-serial fixtures), and the combined `primary|left|right` formatter. Tests run in CI alongside the wheel build.

## 5. Dependencies

- AWS account with permission to create a public S3 bucket and necessary github permissions to setup S3 publish.
- Existing `firmware/pyproject.toml` with the `krabby-firmware` entry point.
- `arduino-cli` core for the Mega 2560 pinned to a known version.

## 6. Deliverables

- Public S3 bucket with at least one mainline build and one release-branch build.
- CI workflow that publishes per branch on each commit.
- Updated `firmware/arduino/arduino.ino` with the `V` command and a generated `version.h`.
- `krabby-firmware` PyPI package implementing `--show`, `--update`, `--update <branch>, --install`.
- `firmware/SETUP.md` updated with bucket layout, `V` protocol, and flash procedure.
