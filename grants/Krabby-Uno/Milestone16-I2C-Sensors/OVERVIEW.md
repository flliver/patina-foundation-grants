# Patina Foundation Grant — Krabby-Uno Milestone 16: I2C Sensors and Battery Management

## Grant Overview
Add a shared I2C sensor cluster to the **primary MCU** of the Krabby-Uno — the Arduino Mega 2560 + Krabby-Uno shield that wins role election as the leader (the FRONT board, on USB to the Orin) — and use it for four things. First, put a SparkFun BMI270 6-axis IMU on the leader's I2C bus and stream accel/gyro/temperature up the **existing** Arduino→Orin telemetry path, because the locomotion model needs body-frame inertial data delivered on the same low-latency serial link as joint state, straight from the MCU, rather than fused on the Orin from the ZED or another camera. Second, add a SparkFun Qwiic OLED 1.3" as the robot's only customer-facing status display, rendering a stylized krab (matching the 3D-printed enclosure face) that shows which of the three controllers are alive and each actuator's state — and, in the process, fix a real firmware bug where an unplugged motor's floating ADC streams noise as if it were a real position. Third, instrument the **octopus** (the robot's main 24 V power bus) with two Adafruit INA228 monitors for total pack and per-battery voltage/current. Fourth, use those measurements to run a battery-protective shutdown/auto-recovery state machine on the MCU, **and** deliver the Orin-side power daemon (started by the same entry point that brings up the HAL server, HAL client, and model) plus the hardware path to actually power the Orin back on — which does not exist today. All of this lives on the **primary MCU only**; the two follower Megas are untouched. Software changes are append-only extensions to telemetry that is already flowing — no new transport, and no invented CLI commands.

## Why is this Important?
- **The locomotion model can't run without an MCU, and it needs the IMU from that MCU.** Inertial data must arrive time-aligned with joint state on the serial telemetry path — deterministic and independent of the vision stack — not clock-synced against ZED frames on the Orin.
- Replaces dead-reckoning on battery state with precise pack and per-battery voltage/current.
- Gives the robot its only at-a-glance physical status UI — so it has to look good.
- Prevents catastrophic over-discharge of LiFePO4 cells without depending on the Orin or any network.
- Closes the gap that `RESUMING` currently can't: with the new power hardware + Orin daemon, the robot can shut itself down cleanly and bring itself back when the pack recovers.
- Establishes a Qwiic daisy-chain pattern (and telemetry/SDK extensions) that scales to more I2C sensors without rewiring.

## Tasks
Full implementation detail, exact code locations, and acceptance criteria live in the task files in this folder. Summaries:

### Task 1 — IMU on the primary MCU, in the telemetry stream → [TASK-1-IMU-TELEMETRY.md](TASK-1-IMU-TELEMETRY.md)
Wire a **SparkFun BMI270** to the **leader Mega only**, via a Qwiic→Dupont adapter on `3.3V / GND / SDA(D20) / SCL(D21)` — the Mega has no Qwiic jack, and the BMI270 is a 3.3 V part. Bring up `Wire` at **100 kHz** (no need for 400 kHz; the model runs ~50 Hz and the payload is tiny), read accel/gyro/temp once per telemetry tick, and **append an `IMU` segment to the leader's existing telemetry line** (append-only, backward compatible). Extend `firmware/interfaces/joint_telemetry.py` to parse it and update the existing telemetry print/GUI — there is no `krabby-cli telemetry --imu` command and none is added. Put all I2C config in a new `firmware/arduino/sensors_config.h`. Capture gyro/accel calibration at boot and persist it in EEPROM. **Do not add a `controller_role` telemetry field** — role-in-telemetry is Milestone 14 (James); this milestone only uses the role locally to drive the OLED.

### Task 2 — Qwiic OLED status display (the customer-facing UI) → [TASK-2-OLED-STATUS-DISPLAY.md](TASK-2-OLED-STATUS-DISPLAY.md)
Daisy-chain the **SparkFun Qwiic OLED 1.3"** (monochrome SSD1306, default I2C **0x3D**) and render a stylized krab matching the enclosure front face: body in three controller-thirds, six legs/hips, battery as two stacks on the rear. Show, for **each of the three controllers**, whether it is detected/active (from role election + telemetry freshness), and a per-actuator state glyph for the intended blue=extend / yellow=retract / green=holding / red=disconnected code (rendered as arrows/filled/hollow since the panel is 1-bit; a discrete red status LED on a spare GPIO gives a true "red" alarm and is reused in Task 4). Fix the disconnected-motor bug: add current-based **attachment detection** (`isConnected()`) and **position-noise filtering** in `firmware/arduino/actuator_manager.h` so a channel with no motor reads as disconnected instead of streaming floating-ADC noise.

### Task 3 — Octopus power bus, shunt, and INA228 monitoring → [TASK-3-POWER-BUS-INA228.md](TASK-3-POWER-BUS-INA228.md)
The **octopus is the robot's main 24 V power bus** (the M12 high-current harness + bus bar). Instrument it with two **Adafruit INA228**: a Pack monitor (`0x40`) across a **200 A/75 mV external shunt** (`setShunt(0.000375, 200.0)`), and a Midpoint monitor (`0x41`) for per-battery voltage. Both onboard shunts disabled (trace cut). **If M12 isn't done, build a bench octopus** — batteries on a table with the shunt wired directly to the bus; the task includes a mandatory **high-amperage battery-safety** section. Append a `BATT` telemetry frame, populate the OLED battery bars, put all addresses/shunt/divergence/cadence in `sensors_config.h`, persist calibration to EEPROM, and commit a wiring diagram + photos to `krabby-research/assets/`.

### Task 4 — Low-power shutdown, auto-recovery, and Orin power control → [TASK-4-POWER-MANAGEMENT.md](TASK-4-POWER-MANAGEMENT.md)
A five-threshold (WARN / SOFT_CUT / HARD_CUT / RECOVERY / OVER_VOLT) state machine. SOFT_CUT signals the Orin (`POWERING_DOWN`), parks the robot, waits ≤ 60 s for `SHUTDOWN_ACK`, then sleeps; a dedicated low-power mode wakes only to poll the **Pack INA228** (no IMU), blinks the red LED + a ~10 s OLED dead-battery splash (stopping below HARD_CUT), and auto-resumes above RECOVERY. Researched and specced the Orin power-on hardware that doesn't exist today — the J4012/J401 can't be back-powered over GPIO, so add a **MCU-controlled supply switch + auto-power-on** (preferred) and/or a **PWR_BTN optocoupler**, with a 60 s no-response force-off. **The Orin-side power daemon is in scope**: it listens for `POWERING_DOWN`, sends `SHUTDOWN_ACK`, and cleanly powers off, started by `hal/server/jetson/main.py` alongside the HAL server + client + model (the same place the collector/teleop threads start). Appendix-C thresholds are validated against the real M12 battery pair.

## FAQ
- **Why does the IMU live on the MCU instead of being fused on the Orin from the ZED?** The model needs inertial data as a proprioceptive input on the same low-latency, time-aligned serial path as joint state. Reading it off the MCU keeps the input deterministic and independent of the vision stack — no syncing IMU samples to camera frames, no dependency on the ZED being up.
- **Why only the primary MCU, not every Arduino?** The body needs one canonical IMU, the operator needs one display, and the pack has one octopus. The leader already aggregates all three boards' telemetry, so it's the only place the cluster belongs; duplicating it on followers adds cost, bus traffic, and ambiguity for nothing.
- **Why 100 kHz, not 400 kHz?** The model runs ~50 Hz and the per-tick I2C payload (IMU + two INA228 + a display refresh) is tiny. 100 kHz has ample headroom, better noise immunity, and tolerates the Qwiic→Dupont run.
- **Why a Qwiic→Dupont adapter?** The Mega + shield has no Qwiic jack; the cable is split out to `3.3V / GND / D20 / D21`. Only the breakout-to-breakout chain uses Qwiic connectors.
- **How is the display "colored" if the OLED is monochrome?** It isn't — the 1.3" SSD1306 is 1-bit. The intended blue/yellow/green/red motor states are rendered as distinct glyphs, and a discrete red status LED gives a true hardware "red" alarm. A future revision could swap in a color display.
- **Why two INA228s?** One on the pack measures total V/I but can't tell a healthy pack from one battery drifting low; a second on the midpoint gives per-battery visibility for one extra board and one sense wire — and each drop-in 12 V LiFePO4 has its own BMS, so divergence between them is exactly the failure to catch early.
- **What's the dependency on Milestone 12?** M12 builds the octopus (power bus) and installs the battery pack. If M12 isn't finished when this milestone starts, Task 3 documents a bench-octopus fallback (batteries + shunt on a table) so the firmware and calibration work proceeds unblocked.
- **Where are the full task details?** In this folder: `TASK-1-IMU-TELEMETRY.md`, `TASK-2-OLED-STATUS-DISPLAY.md`, `TASK-3-POWER-BUS-INA228.md`, `TASK-4-POWER-MANAGEMENT.md`.
